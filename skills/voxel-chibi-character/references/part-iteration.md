# 参考结构与局部迭代

首次建立部件或改变其结构时使用；已有有效记录直接复用，不把每次调色扩展成完整设计报告。

## 把参考变成可建模关系

在 character-spec.json 的 partStructure 中只记录本轮有关的部件。每条包括 id、reference（图/视角或用户纠正）、root、end、landmarks、layer、geometry、motionGroup、uncertainty。用角色地标和相邻部件描述，再在实现时填实际坐标；未知背面记推定，不用母版替代参考。

例：面前鬓发 → 根部在太阳穴，末端到下颌内侧，位于脸外、侧发前；中段稍外张、末端内收。geometry 记录采用体素阶梯或少量硬边斜面及依据；motionGroup 记录根部跟头、自由端如何活动。此例不要求所有角色都有内弯鬓发。

区分三种关系：
- **几何相接**：头顶覆盖发与侧发要遮住头壳，独立运动时保留各自支持面。
- **视觉独立**：悬浮饰件可以留间隙，不能为了绑定添出参考没有的连接块。
- **运动跟随**：饰件可跟随马尾骨骼但保留独立几何、材质；不意味着焊成一件。

左右不同、遮挡关系和用户已确认的长度/厚度优先记录。三缕刘海、无鞋、特定飘带走向等仅属于对应角色，不能升级为全局规则。

## 每次修改的最小闭环

1. 定位实际源码、采用的模型版本及问题视角，保留恢复点。简记本轮 changed / preserved / affected：要改什么、哪些已认可、会影响哪些接界与动态。
2. 优先改语义部件的控制点、厚度或绑定；避免全局缩放、全局换色和重新生成整头来修一个局部问题。
3. 几何与运动分开检查。局部形状改变会影响体素剔面时重新生成；不同运动组之间不能剔掉会暴露的支持面。详见 modeling.md 的“动画前先保证几何”。
4. 先看原问题视角，再看最能暴露副作用的侧/斜视与正常游戏距离；涉及活动端时看原有跑动及停止回稳。只重测受影响项，正式成品仍执行 validation.md。
5. 对比修改前后，区分构建通过、实际画面检查和用户审美认可。出现新穿面或破坏已认可轮廓时修复/回退该局部，不用更亮材质遮盖。

## 选择实现方式

用代码生成几何本身不是缺陷。关键是实际轮廓、面结构与参考关系是否成立。宽发束可使用体素阶梯；小范围转折可使用硬边平面，但连续光滑曲面不能仅凭 low-poly 名称视为体素。头发专题和随包样例提供构造起点，不替代角色参考或正式验收。

## 持续迭代的读取与回写

状态保存在角色工程的 character-spec.json；已有等效设计/验收文件时复用并在 spec 引用，不制造两套冲突来源。skill 保存通用方法，工程保存角色特定决定；不把一次角色纠正写成全局风格，也不依赖自动读取别的聊天。

**开工读取顺序：**本轮用户要求 → 工程当前状态与有效历史纠正 → 对应参考图 → 当前采用的源码/模型。较新的明确纠正替代同一部位的旧要求；不同部位的要求共存，例如“鬓角薄”不能覆盖“外层侧发饱满”。无法取得旧聊天时不虚构认可记录；先从可用证据恢复，无关信息缺失不阻断局部工作。

沿用 iteration.changed / preserved / affected 描述本轮范围；新增 revisionState 保存跨轮状态：

```json
{
  "revisionState": {
    "schemaVersion": 1,
    "currentModel": null,
    "adoptedModel": null,
    "requirements": [],
    "decisions": [],
    "openIssues": [],
    "lastCheck": null
  }
}
```

- currentModel：当前编辑版本的 revision、source、model、preview 与可恢复的 previous；工程相对路径优先。
- adoptedModel：用户已明确采用的版本指针；没有证据时保持 null，旧项目的技术 passed 不构成采用证据。试验只更新 currentModel，不能覆盖 adoptedModel。accepted 可仅涉及部分部件，应继续查看 decisions.parts，不将局部认可扩大为全模型认可。
- requirements：每条含 id、part、request、source、status（active/superseded）、supersededBy（如有）。source 写用户纠正原句/日期或可定位参考；保留被替代关系，避免旧要求重新生效。
- decisions：每条含 revision、parts、result（accepted/rejected/pending）、basis 与恢复路径。用户认可才标 accepted；明确回退的尝试标 rejected，不能作为后续默认。仅认可局部时不要把整模型标 accepted。
- openIssues：未完成问题、对应部位与下一步；解决后移除或标 resolved，不反复执行已经完成的修改。
- lastCheck：记录本次实际检查的版本、视角/动作、结果和残留问题；技术通过与审美认可分别记录。

**实施与结束：**先将本轮纠正并入有效要求，再执行局部改动；完成后更新当前版本、受影响项、检查结果与未解决问题。pending 直到用户表达认可；用户下一次说“其余保留”时按其明确范围继承认可，不为状态登记额外索要确认。回退时同时恢复 currentModel 与受影响部件状态，保留仍有效的用户要求。

对旧工程只补缺失字段，保留未知字段、已有动态配置与历史记录，不运行新建脚手架覆盖旧 spec。交接时提供工程路径和当前版本即可让下一次调用找到状态；跨聊天若工程路径不明，先定位实际工程，不按浏览器最后打开的页面猜采用版本。

### 只读恢复助手

可运行 `python -X utf8 <skill>/scripts/read_revision_state.py <project>/character-spec.json`，提取有效要求、已替代要求、决定、当前版本和待办。该脚本不修改工程，不把 pending 自动变成 accepted；缺少状态会提示定位真实工程。输出后仍需读取它引用的模型、参考和证据，脚本不能裁决自然语言冲突。

### 参数隔离与实际模型回归

需要反复调节的尺寸保存在工程已有参数结构中，以语义部件命名：例如 cheek.depth、outerHair.width/depth、sleeve.freeLength、tail.volume。名称随工程适配，不强制重构既有代码。每项明确影响网格、区域/控制点与固定锚点；一个 SideHair 网格可能同时含贴脸与后侧区域，不能按名字对整网格压缩。共享几何或材质先隔离再修改。

局部修改前后有实际 GLB 时，可用：

```text
node <skill>/scripts/compare_model_parts.mjs <before.glb> <after.glb> SideHair_L SideHair_R
```

末尾为本轮允许改变的真实加载后网格名；其他部件、材质、变换、绑定或烘焙动作改变会报失败。不自动扩大允许名单来通过。允许修改的网格仍检查内部受保护区域，如贴脸减薄时逐顶点或截面对比 XY 轮廓及后侧顶点；不要把整网格在名单中解释为随意改动授权。

工具仅适用于当前无纹理/无 morph 的顶点色 GLB；有纹理或 morph 时显式报错，改用对应验证。运行时物理代码不在 GLB 中，单独保留/比较其实现并执行受影响动态测试。它不证明无穿模或审美合格。Three.js 加载可能规范化名称（如移除点号），源码对导出比较时用显式映射且检查碰撞，不将名字变化误判为丢部件。

`read_revision_state.py --strict` 可在交接检查中让缺失文件、无当前版本、拒绝版本被复用或替代关系异常产生非零退出码；旧项目先恢复状态，不靠删除警告掩盖缺项。完整角色回归和状态测试用于维护 skill，普通局部制作只执行本轮需要的检查。
