# 明日方舟批量模型上传

使用用户指定工作区，默认 `<workspace>`。先读 README.md、handoff.md 和 docs/data-contract.md，按当前真实数据库筛选。六星按干员形态分别计算，默认外观，跳过已有模型，复用已提交会话。

如本技能目录存在 `settings.local.json`，读取其中本机路径/链接作为默认值；用户本轮明确指定优先。配置不随发布包分发，安装或升级时保留。未配置时从当前项目上下文定位，无法确定所需路径再询问；README 列出字段和外部依赖。

## 准备

- 使用已有合格四视图；缺少时调用 `chibi-character-sheet` 生成并实际看图。
- 本地保存角色、图片、批次和会话对应关系。设计交接 JSON 仅留本地，不作为网页必需附件。
- 统一文字来自工作区 `templates/web-model-request.md`（可从本包同名模板初始化），用工作区提供的 `scripts/render_web_model_request.py` 渲染；该脚本属于资料库，不随本包提供。没有脚本时按实际角色/外观和已确认链接填入模板并记录会话，不因此恢复旧附件协议。

## 并行编排与自动选模型

批量任务主动使用 subagent 并行准备不同角色的设定图。主代理负责分配、上传和汇总，角色 worker 负责读取真实参考、调用 chibi-character-sheet、实际看图并保存最终图。每个 worker 一次只处理一个角色，完成后领取下一位；每个角色的概念图与标准化阶段在同一个 worker 上连续完成。

- 并发按当前可用 agent 槽位决定，默认最多 3 个出图 worker，给主代理保留 1 个槽位。当前只有 4 槽时就是 1 主 + 3 子。主代理上传已完成图片时，worker 继续生成其他角色，不等整批图片完成。
- 自动从工具实际可选模型中分配：常规角色解读、出图调用与自检优先 gpt-6-sol / medium；复杂遮挡、服装歧义或失败修订使用 gpt-6-astra / high；纯清单整理优先本地脚本，确需语言处理才用 gpt-6-luna / low。不可用时继承主模型。指定模型的 worker 使用 fork_turns=none，并给完整的角色路径、输出目录和 skill 路径，避免复制整段主对话。
- 上述模型是调度和看图的语言模型；实际图片由当前可用 imagegen 工具生成。工具没有图像模型选择参数时不宣称切换了生图模型。网页建模仍使用已确认的 GPT-6 Pro。
- 每个 worker 写自己的角色目录与结果文件，返回最终图路径及简短检查结论。主代理统一写 catalog 和 batch-handoff，避免多个 worker 同时改总表。
- skill 文件可在各个 worker 中读取，不绑定某一个聊天。每个网页建模会话都带自己的单张图片、同一个 skill 路径和统一短 prompt；一角色一会话，修订和补交继续原会话。
- 浏览器由主代理统一控制，多个角色使用独立标签页，快速逐项上传发送；已提交的网页任务可以同时生成。共享浏览器、剪贴板和文件选择器时不让多个 worker 同时点击。只有工具提供相互隔离的浏览器会话且确认可用时，才分配多个上传 worker。
- 有空槽且有独立角色任务就继续派发。出图与网页上传分别调度，各自处理自身服务的限流。确认网页任务开始后立即推进下一项，不等待模型完成。

## 网页提交

每个角色只提交：**一张最终四视图 + 一个已确认的 Drive skill 路径/文件夹引用 + 统一简短 prompt**。

Skill 路径：使用用户提供或 `settings.local.json` 已确认的 `skill_folder_url`。

统一文字：

> 请按此 skill 将附件的【角色与外观】四视图制作为一个完整角色模型，带轻量动态。双手空置，不重新出图。四肢按 skill 的直方肢体、手部分级与配件包覆标准制作并检查，保留袖形和动画弯肘。交付可编辑工程 ZIP、GLB 与离线 HTML，保留源码和运行时依赖，并按 skill 完成验证。

在普通 ChatGPT 网页选择 GPT-6 Pro，附图、引用上述路径并发送。已确认路径直接复用，不再要求挑选精确 SKILL.md 附件、查版本、核对输入哈希或字节数，也不要求网页生成前先做核对报告。不要追加 BLOCKED_INPUT、BLOCKED_SKILL 或不匹配就停止等门槛；图片经过网页重编码或自动改名不影响制作。

浏览器重复操作可复用工作区实际存在的 `scripts/chatgpt_batch_browser.mjs`；它不随本包提供，缺失时使用当前浏览器工具。发送前记录目标和标签页；发送后保存实际会话 URL 与启动状态，随即继续下一位，不等模型完成。发送结果不明先看原会话，避免重复发出。

## 网页临时限流：继续出图，冷却后续传

遇到 `Too many requests` / `Please wait a few minutes` 时，只暂停网页上传，**继续派发和生成剩余设定图**，完成一张就落盘、登记并加入待上传队列。不能因为网页限流而停止出图 worker、结束整批任务或把暂时冷却当成必须交还用户处理的阻塞。

- 记录网页限流时间、下次尝试时间和当前未发送项。优先遵守网页明确的等待时间；没有具体时间时先冷却约 5 分钟，再用一项待上传图片尝试恢复。再次限流则延长到约 10、20 分钟，之后保持低频尝试；期间继续出图和整理积压，不反复刷新或密集打开新会话。
- 冷却结束后由主代理恢复上传积压设定图，沿用“一张图 + skill 路径 + 统一短 prompt”。先处理已完成图片，成功后逐项发送并适当拉开间隔；恢复一次成功但下一项又限流时，再次冷却，出图仍继续。
- 已确认 started 的角色保留原会话，不重发。发送结果不明的先查看原会话；明确未发送的留在待上传队列。无需重新生成已完成的设定图。
- 只有出图服务自身也限流或报错时，才调整对应出图 worker。全部设定图完成后仍有积压，则继续按冷却节奏等待和续传，直到授权范围内的上传完成，或用户明确停止、出现登录失效等需要用户处理的真实障碍。
- 本次实测曾在等待约 3 分钟后成功上传一项，紧接着再次限流；这表示网页仍需冷却，不表示出图也必须停止。状态分别记录为“出图进行中/已完成”和“上传冷却中”，不要把整批标成已停止。

## 交接

更新 `transfers/<job_id>/batch-handoff.json`，记录已启动、跳过、待准备及真实异常；使用本地脚本完成机械记账。图片与 skill 路径就是新请求的输入，勿重新套用旧三附件/七文件/哈希锁协议。

最终给上传数量和交接路径。之后通过 `ak-model-download` 回收实际生成的工程、GLB 和离线 HTML；不强制网页提供自定义 manifest 或固定七文件命名。
